# 帕斯卡画廊真实案例库设计

## 目标

将网站当前的通用“案例类型”改为真实项目入口。访客先按服务分类浏览项目，再进入具体案例详情，清楚了解帕斯卡画廊在真实项目中解决了什么问题、完成了哪些工作并交付了什么成果。

## 页面层级

采用“案例类型 → 项目列表 → 案例详情”的三级结构：

1. 首页和服务页保留五个服务分类入口。
2. 分类入口进入 `cases.html?service=<服务编号>`，展示该分类下的真实项目。
3. 项目卡片进入 `case.html?id=<项目编号>`，展示该项目的完整公开资料。
4. 同一项目可以属于多个服务分类，但只维护一份详情数据。
5. 案例详情页底部显示相关案例、关联服务和返回案例目录入口。

## 服务分类

案例沿用网站已经确认的五项服务分类：

1. 艺术品销售
2. 艺术品与场地租赁
3. 文旅项目策划
4. 设计
5. 景观艺术品制作施工

分类只承担导航和筛选作用，不再把通用服务方法称为具体案例。

## 分类原则

- 艺术品销售：画廊艺术资源、作品配置及美术馆相关艺术项目。
- 艺术品与场地租赁：艺术空间、展览场地及展览执行项目。
- 文旅项目策划：团泊洼、中新生态城、罗浮宫等目的地和活动策划项目。
- 设计：中原百货、柏典天津等空间、视觉和美陈设计项目。
- 景观艺术品制作施工：棉三雕塑及公共艺术、景观装置项目。
- 一个项目符合多项服务时可归入多个分类，所有入口指向同一详情页。

分类必须以源资料中的实际工作范围为依据；无法确认的归类不公开。

## 案例列表页

`cases.html` 提供：

- 五项服务分类筛选
- 真实项目卡片
- 项目名称、年份、地点、项目类型、简短成果和封面图
- 无结果、数据加载失败和图片缺失的中文状态

从首页某一分类进入时，页面自动选中对应服务；直接访问时展示全部案例。

## 案例详情页

`case.html?id=<项目编号>` 使用统一模板，依次展示：

1. 项目名称、年份、地点和类型
2. 项目概览
3. 项目背景
4. 客户需求或核心问题
5. 帕斯卡负责的工作
6. 策划、设计、制作或实施过程
7. 项目成果与公开交付物
8. 项目图片与图注
9. 关联服务
10. 相关案例

案例编号缺失或无效时显示中文提示，并提供返回案例目录的链接。

## 数据组织

真实项目使用独立公开数据文件管理，不再混入服务方法模板。每项案例包含：

- `id`
- `title`
- `year`
- `location`
- `services`
- `type`
- `summary`
- `background`
- `challenge`
- `responsibilities`
- `process`
- `outcomes`
- `deliverables`
- `images`
- `sourceFiles`
- `publicStatus`

首页、案例目录、案例详情和服务页读取同一份案例数据。源文件路径仅用于内部核对，不在公开页面显示。

## 图片与资料边界

- 只使用用户提供资料中可以确认属于该项目的图片。
- 不使用融资金额、报价、成本、估值、股权、财务预测或投资条款。
- 不公开无法确认授权的敏感客户资料、联系方式和内部工作文件。
- 事实不完整时不编造；公开页面省略无法确认的字段，内部记录标明资料缺口。
- 图片不足时显示统一中文占位状态，不使用无关图片替代。

## 视觉与交互

- 延续全中文、白色背景和鲜绿色点缀。
- 列表卡片清楚显示“查看案例”，可点击区域明确。
- 详情页以真实项目图片为主要视觉；没有图片时使用克制的文字占位。
- 桌面和手机端均不得出现横向滚动、文字截断或导航重叠。

- 每个首页案例类型都能进入已筛选的真实项目列表。
- 每个项目卡片都能进入有效的案例详情页。
- 同一项目可以出现在多个分类且指向同一详情。
- 服务页相关案例链接有效。
- 无效案例编号、无结果和图片缺失状态均为中文。
- 页面不再把通用服务描述标记为具体案例。
- 所有公开事实能够追溯到用户提供的资料。
- 自动化测试、脚本语法检查、桌面和手机浏览器检查全部通过后，才发布到 GitHub Pages。
